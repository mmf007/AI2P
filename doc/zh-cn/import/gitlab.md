# 从 GitLab 导入任务 — 接入说明

导入把 **GitLab 的任务**（issue）搬进 AI2P 的任务（技术规格 2.10 节，第 11 章）。接入需要
GitLab 给出的一个字符串 — **个人访问令牌** — 以及导入源名录中的一条记录。
云端的 `gitlab.com` 和自建的 GitLab 服务器都能用。

## 1. 获取访问令牌

GitLab 在个人资料设置中发放令牌：

1. 在浏览器中登录 GitLab 并打开
   <https://gitlab.com/-/user_settings/personal_access_tokens>
   （自建服务器 — 从它的地址走同样的路径：`https://git.example.com/-/user_settings/personal_access_tokens`）。
   界面里也提示了这个页面的路径：**头像 → Edit profile → Access tokens**。
2. 点击 **「Add new token」**。填写：
   * **Token name** — 任意，例如 `AI2P import`；
   * **Expiration date** — 有效期；到期后令牌就不再工作，导入会
     回答「GitLab 未接受**令牌**」；
   * **Select scopes** — 有 **`read_api`** 就够了。完整的 `api` 也可以，但它给出
     修改数据的权限，而导入只做读取。
3. 点击 **「Create personal access token」** 并**立刻复制**显示出来的值：
   GitLab 不会再显示第二次。现在的令牌以 `glpat-` 开头。

令牌可以访问您的项目 — 请像保管密码一样保管它。

**项目令牌或群组令牌**（项目内的 Settings → Access tokens）同样可用，前提是
它有 `read_api` 权限；它的好处是只看得到恰好一个项目。

## 2. 在导入源名录中创建源

**设置 → 「名录」标签页 → 「导入源名录」 → 「添加」：**

| 字段 | 填什么 |
| --- | --- |
| 源名称 | 任意，例如 `GitLab 主源` |
| 类型 | GitLab |
| GitLab 服务器 | 留空 — 云端的 `https://gitlab.com`；自建服务器要写全，例如 `https://git.example.com` |
| GitLab 项目 | 形如 `组/项目` 的项目路径 — 与地址栏中看到的完全一致；子组用斜杠分隔（`组/子组/项目`） |
| 标签 | 按标签筛选任务，用逗号分隔，例如 `bug,ui`；留空 — 项目的全部开放任务 |
| 已启用 | 暂时不可用 — 完成第 3 步后会自行开启 |

点击 **「保存」**。输入令牌的按钮只在**已保存的**记录上出现：值
会立刻放进密钥库，所以在保存之前无法知道它属于谁。

**GitLab 没有单独的「API 密钥」** — 这一点和 Trello 不同，那里密钥和令牌是两个不同的
值。所以 GitLab 源的表单里只有一个密钥按钮，而源只凭输入的一个令牌
就能启用。

## 3. 输入令牌

用 **「修改」** 按钮打开已保存的源 — 表单中出现了
**「设置令牌」** 按钮。粘贴第 1 步得到的字符串并点击「保存」。

旧值永远不会显示 — 要替换令牌，就输入一个新的。表单下方
可以看到状态：「令牌：已设置，来源 — 组织」。如果值不像
GitLab 的令牌（不以 `glpat-` 开头），表单会提出警告：这是提示，不是禁止 —
项目令牌和 OAuth 令牌长得不一样，但照样能用。

**「检查连接」按钮**（在旁边，输入令牌后才能用）会向 GitLab 询问
「我是谁」，如果源中指定了项目，还会问这个令牌能否看到它。回答会用
文字给出：令牌是否被接受、它发放给了哪个账户、项目是否可见。在这里检查连接，
比在第一次导入时才碰到拒绝要划算。

**这个值存放在哪里。** 在您组织的数据库中，用组织的密钥**加密**保存
（和模型的 API 密钥一样）：它会自己复制到组织的所有服务器上，
而只有拿到组织密钥的服务器才能解密它。不需要往
`secrets.json` 里写任何东西。

**两个 GitLab 账户或两台 GitLab 服务器。** 每个源都有**自己的**令牌引用 —
创建第二个源（例如给自建的 GitLab 服务器用）并在其中输入另一个
值即可。按链接导入单个任务时，会根据链接中的服务器地址自行选择源。

## 4. 启动导入

1. 选择**项目**（在顶栏或项目标签页中） — 导入总是进入当前的
   AI2P 项目。
2. 在任务列表中点击**带箭头的云**图标按钮（「导入任务」） — 它只在
   选定了项目时才可见。
3. 在对话框中选择源和复选框：
   * **添加新的**（默认开启） — 还不存在的任务会变成 AI2P 的任务；
   * **更新已有的** — 先前导入的任务会从 GitLab 更新标题、描述
     和期限（这些字段的本地修改会被覆盖）。
4. 点击 **「导入」**。结果会以消息显示：「新增 X，更新 Y，
   跳过 Z」；「作业历史」中会出现一条 `import.run` 记录。

## 究竟会导入什么

* 取指定项目中的**开放任务**（`state=opened`）；如果设了标签 —
  只取带这些标签的。
* GitLab 任务 → 状态为**「草稿」**的 AI2P 任务：标题、期限（`due_date`）、
  **正文本身**（issue 的文字）放进描述 + 底部的来源附注
  （「从 GitLab 导入：项目 …，任务 #N」，带链接）。执行者和优先级
  由您在 AI2P 里填。
* **附加的文件。** GitLab 的 issue 没有单独的附件列表：上传的文件
  以 `/uploads/<哈希>/<名称>` 的链接形式活在**正文之中**。导入会找出这样的链接，
  把文件**下载**到 AI2P 的项目存储中，并把链接改写为本地的 — 图片
  仍然是图片。下载不成功的文件（没有权限、大于 200 MB）会保留为
  指向 GitLab 的链接：是完整的而不是相对的 — 至少还能点过去。
* **讨论。** 任务的评论会转入 AI2P 的**任务聊天**：作者显示
  为 `gitlab:<登录名>`，时间和顺序都保留。GitLab 的系统记录（「修改了标签」、
  「指派了执行者」、「关闭了」）会被跳过 — 那不是人的对话。再次导入
  只添加**新**消息，不会产生重复。
* **不会产生重复**：任务的外部键以
  `gitlab:<服务器>:<项目>:<编号>` 的形式记住；再次导入同一个任务时会跳过或更新它 —
  取决于复选框。服务器被有意写进键里：您自建 GitLab 的第 42 号任务和
  云端的第 42 号任务是不同的任务。

## 按链接导入单个任务

在任务列表中，批量导入按钮旁边有一个 **「按 URL 导入任务」** 按钮：

1. 粘贴形如 `https://gitlab.com/<组>/<项目>/-/issues/<编号>` 的链接。可以识别
   子组、不带 `/-/` 的旧式地址、`?…` 和 `#note_…` 尾巴，以及自建
   GitLab 服务器的地址。只有当已启用的 gitlab 源有多个、并且按服务器地址
   无法选出唯一一个时，才会再问用哪一个。
2. 任务的内容会填入**新任务表单**：标题、放进描述的正文、
   期限、下载好的文件。讨论会在任务保存之后立刻进入聊天。
3. 补全表单（执行者、优先级）后保存。再次导入同一个任务
   不会产生重复。

AI 智能体也能用 `import_task_from_url` 工具执行同样的动作（动作代号
`AI2P.Tasks.ImportFromUrl` — deny/confirm 安全规则照常适用）。
用哪个程序来导入，由**链接的形态**决定：智能体不需要知道有哪些
源被建好了。

## 从 GitLab 更新任务

导入进来的任务填有**导入链接**（任务表单的「扩展」一节，
卡片顶部的一行）。这种任务卡片中的 **「刷新」** 按钮会**追问**：

* **「从导入源」** — 重新读取 issue，并把标题、期限、
  描述（连同新下载的文件）和讨论中的**新**消息放进任务；
* **「仅本地」** — 只是重新读取任务，不去问 GitLab 任何事情；
* **「取消」**。

更新时描述会被**整体**重写 — 与勾了「更新已有的」的批量导入
完全一样。验收标准、执行者、状态、优先级、
标签和任务的各种关联，更新**不会**去动：它们在这里维护，而不是在 GitLab。

清空「导入链接」字段 — 任务就与源解绑了，也不会再有追问。

## 如果有什么不工作

| 消息 | 原因和处理办法 |
| --- | --- |
| 「未找到 GitLab 令牌（…）」 | 令牌没有输入：打开源并点击「设置令牌」（第 3 步）。旧安装 — 请检查 `secrets.json`：文件路径直接写在消息里。 |
| 「本服务器尚未收到组织密钥…」 | 服务器接入了别人的组织，但申请尚未被其指挥服务器确认 — 没有组织密钥就无法加密这个值。请确认接入（设置 → 服务器）。 |
| 「GitLab 未接受**令牌**（HTTP 401…）」 | 令牌不正确、已被吊销或**已过期**，又或者它没有 `read_api` 权限。请签发一个新的（第 1 步）。常见原因是复制错了值：消息会显示所输入值的长度（值本身永远不会显示）。 |
| 「GitLab 拒绝访问（HTTP 403…）」 | 令牌被接受了，但它的持有者对该项目没有权限，或者令牌没有 `read_api` 权限。 |
| 「GitLab（…）未找到所请求的内容（HTTP 404…）」 | 项目路径或任务编号不对。**令牌持有者看不到的非公开项目同样返回 404** — GitLab 有意不透露别人项目的存在。 |
| 「GitLab 回应『请求过于频繁』（HTTP 429）」 | 请求频率上限。请等一分钟后重试。 |
| 「导入源未指定 GitLab 项目」 | 「GitLab 项目」字段是空的 — 批量导入没地方取任务。请填写形如 `组/项目` 的路径。 |
| 「链接 … 不像是 GitLab 任务」 | 地址没有指向 issue：需要 `.../-/issues/<编号>` 这种形态。指向 merge request、看板或史诗的链接不行。 |
| 导入完成了，但「新增 0」 | 标签没有命中任何任务，或者项目里没有开放的任务；请试试把「标签」字段留空。 |
| 描述中的文件打不开 | 文件没有下载成功（没有权限、大于 200 MB） — 描述里留下的是指向 GitLab 的链接，只有登录了 GitLab 的人才打得开它。原因写在日志里。 |

消息会完整地出现在导入窗口本身 — 不必从悬浮提示里去捞。请求的细节在应用日志中
（`logs/*.jsonl`，`GitLabImporter` 记录）：请求了哪个地址、令牌是从哪里取的、
它有多长（值本身永远不会写进日志），GitLab 回答了什么。

## 在这个导入中 GitLab 与 Trello 有什么不同

| | Trello | GitLab |
| --- | --- | --- |
| 密钥数量 | 两个：API 密钥 + 令牌 | 一个：个人令牌 |
| 密钥怎样送出 | 作为查询字符串的参数 | 作为 `PRIVATE-TOKEN` 请求头 |
| 源指定什么 | 登录名和看板名称筛选 | 服务器地址、项目路径、标签 |
| 导入的单位 | 看板的卡片 | 项目的任务（issue） |
| 附件 | 卡片上的单独列表 | 正文之中的链接 |
| 任务的外部键 | `trello:<卡片 id>` | `gitlab:<服务器>:<项目>:<编号>` |
