# AI2P 安全策略

## 受支持的版本

安全修复只针对 AI2P 的**最新发布版本**（仓库的 Releases 页面）。以前的版本不再修复 — 请更新到
最新版本：覆盖安装到原有版本之上会保留数据、设置和密钥。

| 版本 | 是否受支持 |
|---|---|
| 最新发布版 | 是 |
| 所有更早的版本 | 否 |

## 如何报告漏洞

**不要提交公开的 issue**，也不要在 Discussions 中写漏洞的事：在修复发布之前，公开的描述会帮助
想要利用它的人。

请通过以下任一方式私下报告：

1. **GitHub → Security 选项卡 → Report a vulnerability**（Private vulnerability reporting）—
   主要方式。只有仓库的维护者能看到这条报告。
2. **电子邮件** — 发送到 GitHub 上仓库所有者个人资料中注明的地址，主题为
   「AI2P security」。

报告中请附上：

* AI2P 的版本（安装目录中的 `version.json` 文件）和操作系统；
* 具体什么地方存在漏洞，以及它会造成什么危害；
* 复现步骤或示例（请求、文件、任务文本）；
* 如果您知道 — 建议的修复方法。

## 响应时限

* 确认收到 — **7 天**内；
* 初步评估（是不是漏洞、有多严重）— **30 天**内；
* 修复会在最近一次发布中推出；具体时间我们会与您商定，在修复发布之前请不要公开细节。
  如果您愿意 — 我们会在发布说明中注明您。

## 威胁模型：AI2P 保护什么，不保护什么

AI2P 是一个本地程序：服务器运行在您的计算机上，它启动的 AI 代理也运行在同一台计算机上。
由此产生了一些保护边界，需要事先了解。

**CLI 代理以服务器的用户身份运行。** 命令行代理（Claude Code 及其他 CLI 执行者）作为单独的进程
启动，使用与 AI2P 服务器相同的操作系统账户，没有沙箱，也没有单独的隔离。任务的安全规则
（允许和禁止的目录、操作）作用于 AI2P 自己的工具，并在作业中传达给代理，但**操作系统并不强制
执行它们**：代理自身的手段（读取文件、搜索、shell）不受项目工作目录的限制。也就是说，代理
**可以读取项目之外的文件** — 这个账户能访问的一切，包括主目录中的密钥和令牌。发行版中的
配置文件会以无需确认的编辑模式启动代理。

在实践中这意味着：

* 如果不是机器上的一切都可以交给代理，请用一个**单独的操作系统账户**运行 AI2P 服务器，
  不让它访问他人的和个人的数据；在 Linux 上可以在容器中运行，只把项目目录挂载进去；
* 不要在这台机器上保存不能让代理看到的机密；
* 对 CLI 代理来说，「禁止」/「询问」规则是约定，而不是屏障；屏障是操作系统的权限；
* 从外部系统（Trello、GitHub、GitLab、Figma）导入的任务文本，是来自外人的输入：其中可能包含
  代理会照着执行的指令（prompt injection）。在把来自他人来源的任务交给代理之前，请先检查它们。

**服务器与网络。** 默认情况下 UI 和 API 只监听 `localhost`。访问 `/api` 需要登录。
把服务器开放到网络中时（多台服务器、从手机访问），请启用 HTTPS（见管理员手册中的「HTTPS」），
并且不要在没有自带防护的反向代理的情况下把服务器发布到互联网上。

**机密。** API 密钥和管理员密码以明文形式保存在安装目录的磁盘上（`secrets.json`、`secrets/`），
受服务器用户的权限保护（在 Linux 和 macOS 上为 `0600`）。它们的保护手段是文件系统权限和
磁盘加密。

我们认为属于漏洞的是对这些边界的绕过：未登录即可访问 API；在 AI2P 承诺用自己的工具遵守规则的地方，
代理越出了规则；机密泄漏到日志、任务或发往另一台服务器的副本中；由导入或复制的数据导致代码被执行，
等等。CLI 代理读取其账户下的文件，是上文所述的特性，而不是漏洞。
