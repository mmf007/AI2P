# 插件与 MCP

**「设置 → 插件与 MCP」**标签页，是把一切外部东西接进 AI2P 的地方：装在您计算机上的程序
（视频编辑器、ffmpeg 转换器），以及自带工具的 MCP 服务器。

这一节的意义用一句话说清楚：**AI 智能体获得新的动作，而这些动作是要授权的**。插件不是一个
「想干什么就干什么」的扩展：它带来的一切都要经过动作目录和任务的安全规则。

## 插件由什么组成

一条插件记录同时是四样东西：

| 组成部分 | 存放在哪里 | 带来什么 |
|---|---|---|
| **动作** | 动作目录、安全规则 | AI 智能体的新工具 |
| **经验条目** | 组织的通用经验 | 智能体知道怎么用这些工具 |
| **程序** | 软件包目录和本服务器的 `config.json` | 插件要调用的外部程序 |
| **文档** | `doc/<语言>/plugins/<代码>.md` | 说明文档，列表行里的 **「i」** 按钮 |

前两部分是**组织的属性**：它们存在数据库里，并复制到所有服务器。第三部分是**本计算机的属性**：
找到的程序及其路径保存在本服务器的 `config.json` 中，从不复制。集群里邻居机器上的同一个程序
装在别的路径，而且有一半服务器根本没有它。

插件本身的描述以**清单文件**的形式到来：数据目录下的 `plugins/<代码>/plugin.json`。清单列出
动作、指明所需程序、声明记录的设置；它不能在本节里手工修改 —— 动作及其参数只能随清单一起变。

发行包里带了六条记录：通往 **Shotcut / Kdenlive**、**DaVinci Resolve**、**Blender VSE** 和
**OpenShot** 的网关，**视频转换器（ffmpeg）**，以及 **LoRA 适配器训练器
（musubi-tuner）**。

## 两类记录：网关与 MCP 连接

| | **网关**（`gateway`） | **MCP 连接**（`mcp`） |
|---|---|---|
| 外面是什么 | 本机上的一个程序 | 一台 MCP 服务器（自己的进程或网络地址） |
| 动作列表从哪来 | 来自清单，是固定的 | **从服务器本身获取**，列表是动态的 |
| 要它工作需要什么 | 找到或安装程序 | 连接上并获取工具列表 |
| 密钥 | 不需要 | MCP 服务器令牌（如果它要求） |
| 工作在哪里算 | 在我们这边：我们写文件并调用程序 | 在对面 |

值得记住的差别是：网关的能力集合事先就已知道，只有 AI2P 出新版本时才会变；而 **MCP 服务器的
能力集合随时可能变**。因此 MCP 的工具列表要靠**人明确的动作**来获取 —— 「刷新工具列表」按钮
—— 而且它会显示新增了什么、消失了什么。MCP 服务器无法悄悄给自己添一项新能力。

## 本服务器上的状态

| 状态 | 含义 |
|---|---|
| **已声明** | 磁盘上有清单，但还没有组织记录 —— 插件尚未初始化 |
| **正在查找软件** | 记录已存在，但本服务器上没找到所需程序，也没有指定路径 |
| **已初始化** | 一切就位：动作已登记、经验已写入、程序已找到 —— 工具已发布给智能体 |
| **已停用** | 人把插件暂时关掉了；工具不发布，各项记录保留 |
| **已移除** | 动作和经验条目已在整个组织中删除 |

状态是**各服务器各有各的**：装了 Blender 的那台机器上插件是「已初始化」，隔壁那台则是
「正在查找软件」。这正是分布式工作的意义所在：一个人拍，另一个人剪。

此外还可能出现**没有清单**的一行：记录是通过复制到达的，而文件 `plugins/<代码>/plugin.json`
不在这台计算机上。这一行是特意显示出来的 —— 否则在这里根本无从得知邻居机器上正在工作的插件。

## 如何初始化

1. 打开**「设置 → 插件与 MCP」**。列表由本服务器磁盘上的清单和组织的记录合并而成。
2. 在插件那一行按**「初始化」**。系统会建立组织记录，为每个动作在动作目录中登记一条，并把插件
   的经验条目写入组织的通用经验。对 MCP 类型的记录，首先做的是获取工具列表：只有在目录中登记
   过的东西才能发布给智能体。
3. 用下面三种办法之一给插件配上程序：
   * 插件在 `PATH` 里**自己找到**并校验了版本 —— 什么都不用做；
   * **「安装」** —— 如果插件带软件包（便携版 Shotcut 就是这样装的，ffmpeg 也是）；
   * **「指定程序已安装的位置」** —— 手工填路径；程序文件和安装目录都可以。DaVinci Resolve
     就是这样接入的：它的安装包要填注册表单才能拿到，我们没法替您下载。
4. **「检查」**按钮会重新执行查找，并显示找到了什么。

初始化是**服务器管理员的动作**。读者能看到这一节，但里面没有按钮：登记动作等于授权，不是调整
外观。

必须**在每一台需要该插件工作的服务器上**都做一次：组织记录会自己复制到邻居机器，程序和它的路径
不会。

## 「本服务器上未找到该程序」

这一行不是错误。它的意思正如字面：这台计算机上没有所需程序，也没有指定它的路径。只要还是这样，
**插件的动作就不会发布给智能体** —— 一个注定回答「拒绝」的工具，只会白白浪费智能体的一轮。

该怎么办：

* 如果有软件包，用**「安装」**按钮装上；
* 自己装好，再用**「指定程序已安装的位置」**告诉它路径；
* 什么也不做 —— 如果这台机器上本来就不做剪辑：让任务跑到插件已初始化的那台机器上去。

版本校验是查找的一部分：低于最低可用版本的程序算作没找到。这不是挑剔，而是防止半小时的运算之后
才收到拒绝：ffmpeg 的参数集合在 4.x 与 7.x 之间变过，`melt` 的在第六版与第七版之间变过。

## MCP 只能通过我们的记录接入

规则简单而强硬：**MCP 服务器只能用插件记录接入，别无他法。**

直接写进 CLI 代理配置（绕过 AI2P）的 MCP 服务器，会绕过我们全部的安全机制：它的工具既不在动作
目录里，也不在任务规则里，更不在日志里。智能体在用，而您既不知情，也无法禁止。所以那种接法不是
「另一种配置方式」，而是一个窟窿。

我们这边是这样做的：

* MCP 服务器的工具会被整份取回，并为每个工具登记一条**动作目录条目** —— 从那一刻起，它就可以
  用任务或项目的普通安全规则来允许或禁止；
* **插件工具的策略是反过来的**：没有目录条目的工具是**禁止**的。系统的普通工具规则是另一条
  （没有条目就没有禁止），而正因如此，插件这里要反过来：否则某个 MCP 服务器在新版本里加进来的
  工具，就会悄无声息地绕过规则；
* 从列表里消失的工具，其目录条目会被撤销 —— 它既不发布，也不被允许；
* MCP 服务器的**令牌**保存在本服务器的 `secrets/` 子目录中，不参与复制，也绝不会进入
  `config.json` 或日志；
* **工具列表是按服务器各自保存的**（存在 `config.json` 里）：MCP 服务器在装有它程序的那台机器上
  启动，邻居机器上的版本可能不同。参与复制的不是列表，而是它的结果 —— 动作目录中的条目。

## 长时间运行：程序作为任务的执行者

插件的动作是 AI 智能体的工具：智能体调用一个动作，几秒钟就能拿到回应。训练 LoRA 适配器不是
这样 —— 它要跑好几个小时，并且独占整块显卡。因此插件还有第二类能力：**长时间运行的操作**
（清单中的 `run` 区块）。调用它们的不是智能体，而是**任务** —— 由第三种类型的执行者
**「自动软件」**来做（见[执行者](performers.md)）。

这种操作比普通动作多出来的东西：

* **工作目录** —— 相对路径从项目文件夹算起，绝不允许跑到它外面；
* **两个上限，而不是一个**：**沉默**超时与总时长上限分开。只要程序还在打印，它就还活着；
  真正卡死的应当在半小时后变成错误，而不是十二小时后；
* **结果解析规则** —— 指定的输出、清单里给出路径的文件，或者「目录中按掩码最新的那个文件」。
  第三种正是为训练器准备的：轮次文件的名字（`epoch-0007.safetensors`）事先叫不出来；
* **「单实例」**标记 —— 插件表单里的一列。只要这种操作正忙，带着它的第二个任务就在队列里
  **等待**。这不是「慢一点」：同一块显卡上跑两个训练，一分钟内就会因显存不足而失败。

**程序计算时能看到什么。** 它的输出被不间断地读取，并同时送往两个地方：任务卡片的
**控制台** —— 实时、一行一行地显示，以及**作业日志** —— 永久保存。日志不必等工作结束就能
查看。停止用的是普通的停止任务按钮，按下时整棵进程树都会被结束。返回码非零、沉默超过上限、
总时间耗尽，这三者同样都会变成作业错误，输出的最后几行就放在错误文本里 —— 没有它们，
「崩了」是修不好的。

和动作一样，操作也没有自己的命令行：参数写在清单里，任务只能往里代入已声明的记录设置和项目
文件夹内的路径。

**插件记录并非只能手工创建。** 安装一个声明了 LoRA 训练软件包的模型时，系统会自己创建那个
指向全部这些软件包的**训练器插件**的记录，并把找到的程序路径写下来 —— 但**只写入空字段**：
人工指定过的路径，重复安装不会覆盖。记录出现时处于**「已声明」**状态 —— 名录动作和经验条目
仍然由「初始化」按钮创建：向智能体发布工具是人的决定，而不是安装的副产品。

## 「插件与 MCP」安全规则

安全规则为本节准备了单独的一类 —— **对插件与 MCP 的访问**。普通规则回答的是「究竟允许
智能体做什么」（动作代码），而这一类回答的是「**到底允许使用哪些插件**」。

* **样式**是插件代码（`trainer.musubi`）或带操作的代码（`trainer.musubi:lora.train`）。
  通配符和正则表达式的用法与其他类型的规则相同。
* **操作有两个，至少要勾选一个**：「**使用**」—— 智能体调用插件的工具；「**运行**」——
  「自动软件」任务启动程序。第二个是在程序启动**之前**检查的，一次覆盖所有路径：智能体、
  人、层级队列和延迟启动。
* **默认全部允许。** 没有这一类规则就意味着可以；禁止要显式建立。规则可以放在三个层级中的
  任何一个（组织、项目、任务），叠加时以更严格的为准。
* 在启动程序这件事上，「**追问**」等于**拒绝**：启动来自队列，那里没有人可问。

这条规则在与其他规则相同的表单里创建：设置 → 安全（整个组织）、项目卡片 →「安全」、
任务卡片 →「安全」。

## 停用、启用、卸下

* **「停用」** —— 临时的：工具不再发布给智能体，目录条目和经验条目原地保留。恢复用**「启用」**。
* **「卸下」** —— 彻底的：插件的动作和经验条目会**在整个组织中**被删除。记录设置和程序路径会保留，
  这样再次初始化不必从零开始。

插件写入组织通用经验的那些条目，可在**「设置 → 通用经验」**标签页中查看和修改；插件表单上的
「打开通用经验」按钮通向同一个地方。
