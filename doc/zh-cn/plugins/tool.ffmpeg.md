# 视频转换器（ffmpeg）— 插件 `tool.ffmpeg`

**它做什么：** 为剪辑准备素材 —— 把片段转成剪辑用中间格式、提取音轨、按列表拼接、把片段统一到
共同的画幅与帧率。

**为什么需要它。** 我们生成的是 mp4/H.264，音频是 aac/mp3（fal.ai、ComfyUI、`SaveAudioMP3`）。
而 Linux 版免费 DaVinci Resolve **根本不解码 H.264/H.265**，AAC 连付费的 Studio 都不支持，
Blender 各种构建自带的编码器也各不相同。转换器让「生成 → 剪辑」这一环不再取决于某台机器上某个
剪辑软件构建的能力：进剪辑之前，素材先过一遍 ffmpeg。

---

## 动作

动作是**窄而具名的**。每个动作都完整写在插件清单里：ffmpeg 的参数来自发行版文件，工作参数来自
记录设置，而 AI 智能体只提供**路径**，而且每个路径都要检查。

| 智能体工具 | 做什么 | 接收什么 | 产出什么 |
|---|---|---|---|
| `ffmpeg_to_edit` | 转成剪辑用中间格式 | `in` — 文件，`out` — 输出到哪（可选） | `<名称>_edit.mov`：DNxHR 或 ProRes，配无压缩音频 |
| `ffmpeg_extract_audio` | 提取音轨 | `in`、`out` | 无压缩的 `<名称>_audio.wav` |
| `ffmpeg_concat` | 按列表拼接 | `files` — 路径列表，或媒体库筛选（`scene`、`kind`、`tag`），`out` | `ai2p_concat.<源文件扩展名>` |
| `ffmpeg_uniform` | 统一画幅与帧率 | `in`、`out` | 指定尺寸与帧率的 `<名称>_uniform.mov` |

**「执行 ffmpeg 命令行」这个动作没有，将来也不会有。** 那等于允许执行任意代码并写文件，任何安全
规则都收不住它：ffmpeg 有 `-f lavfi`，有 `file:`、`concat:`、`tcp:` 协议，还有可以覆盖任何文件
的 `-y`。向智能体索要这样的命令没有意义——它不存在；需要别的工作配置，就去改**插件记录的设置**。

### 常规顺序

1. 对每个片段用 `ffmpeg_uniform` —— 统一画幅与帧率。
2. `ffmpeg_concat` —— 拼接。它**不重新编码**（只复制流），所以各段必须格式一致；格式不同的片段
   拼不起来。
3. `ffmpeg_to_edit` —— 生成进剪辑软件用的中间格式。
4. `ffmpeg_extract_audio` —— 如果需要把音频作为单独轨道。

## 记录设置

在**「设置 → 插件与 MCP」**的记录表单里设置；任务文本里改不了。

| 键 | 默认值 | 含义 |
|---|---|---|
| `videoCodec` | `dnxhd` | 中间格式编码器：`dnxhd`（DNxHR）或 `prores_ks`（ProRes） |
| `videoProfile` | `dnxhr_hq` | profile：DNxHR 用 `dnxhr_lb`/`sq`/`hq`/`hqx`，ProRes 用 `0`–`3` |
| `pixelFormat` | `yuv422p` | 像素格式 |
| `audioCodec` | `pcm_s16le` | 音频编码器（无压缩 PCM） |
| `audioRate` | `48000` | 采样率，Hz |
| `width`、`height` | `1920`、`1080` | `ffmpeg_uniform` 使用的共同画幅 |
| `fps` | `25` | 共同帧率 |

**默认选 DNxHR 而不是 ProRes**，因为 ffmpeg 的 ProRes 编码器（`prores_ks`）在 Windows 和 Linux
上产出的文件 Resolve 并不总能读，而 DNxHR 是 Avid 的原生格式，本分支的所有剪辑软件都收。

**「profile ↔ 像素格式」是成对的：** `dnxhr_hq` 要求 `yuv422p`，而 profile 3 的 `prores_ks`
要求 `yuv422p10le`。不匹配由 ffmpeg 自己拒绝，拒绝信息智能体在工具回答里能看到。

## 文件写到哪里，以及什么是禁止的

* 结果默认放在**源文件旁边**（素材按场景分文件夹，跑到项目根目录的文件得人工去找），文件名带上
  后缀 `_edit`、`_audio` 或 `_uniform`。
* 输入路径和输出路径**只允许在项目目录内**，或者在**任务安全规则**开放的外部目录内。其余一律
  拒绝，而且是在启动程序之前。
* 结果**绝不覆盖源文件**：带 `-y` 的 ffmpeg 会在读取之前就把它写成空文件，而无声丢失素材比拒绝
  更糟。
* 任务的安全规则在这里同样有效：禁止读取的子目录，转码也读不了。

## 长时间转换

转换器以**独立进程**运行，因此不会卡住任务。每 15 秒在任务调用日志里记一次进度（「已处理素材
N 秒」）；等待时间用尽后（默认每个操作 2 小时）进程被停止，智能体收到明确的拒绝，并被告知已经
处理了多少素材。这一点很重要：只说「没做完」，无法区分是程序卡死还是本来就慢。

## 操作系统方面的限制

ffmpeg 的各种构建**自带的编码器并不相同**，这不是小事：非自由编码器和 GPL 编码器在某些构建里
完全没有。我们这四个操作依赖的是**任何**构建都有的编码器（`dnxhd`、`prores_ks`、
`pcm_s16le`/`pcm_s24le`）以及内置的 H.264/H.265/AAC 解码器，所以即便是精简构建，转换器也能用。
若将来需要反向导出成 H.264/H.265，就需要带 `libx264`/`libx265` 的构建（GPL 许可）：LGPL 构建里
没有它们。构建里有哪些编码器，用 `ffmpeg -encoders` 就能看到；缺少的编码器 ffmpeg 会直说
（「Unknown encoder」），拒绝信息也会传到智能体那里。

**Windows。** 程序由我们的 `ffmpeg` 包用「安装」按钮装上：来自
https://www.gyan.dev/ffmpeg/builds/ 的 `ffmpeg-9.0.1-essentials_build.zip`
（111 253 802 字节，里面有 `ffmpeg.exe` 和 `ffprobe.exe`）。已实机验证：版本 9.0.1，需要的
编码器一个不少。链接带版本号——用会变的链接就意味着每个人的版本都不一样。

**Linux。** 我们没有安装包：ffmpeg 用系统自带方式安装 —— `apt install ffmpeg`（Debian、
Ubuntu）、`dnf install ffmpeg`（Fedora，需要 RPM Fusion）。这里的坑是**仓库里的版本**：Debian 12
带的是 5.1，而插件需要 **6.0 及以上**，找到的 5.1 会被版本检查拒掉 —— 这时请安装较新的构建
（例如 https://johnvansickle.com/ffmpeg/ 的静态构建），并在插件表单里手工指定路径。Linux 上
没有实机验证。

**macOS。** 我们没有安装包：`brew install ffmpeg`，之后路径会被自动找到，或者手工指定。没有
实机验证。

**任何系统上版本检查都是必需的。** ffmpeg 的参数集在 4.x 与 7.x 之间变化明显，悄悄找到的旧程序
会在任务执行过程中把工作弄砸 —— 而人们却会到插件里去找原因。

## 程序是怎么找到的

1. **手工路径**，如果在插件表单里填了（本服务器 `config.json` 中的 `ffmpegPath`）—— 填程序文件
   或它所在的目录都可以。
2. **在本服务器上查找**：PATH 中的 `ffmpeg` 命令，用 `-version` 询问版本，且必须不低于 6.0。
3. **用 `ffmpeg` 包安装** —— 插件表单里的「安装」按钮（Windows）。

找到的路径**绝不会进入组织的数据库**：它保存在这台计算机的 `config.json` 里。插件的描述会复制到
组织的所有服务器，而安装始终是本地的——「这里装了没有」，每台服务器各有各的答案。

只要程序没找到，插件**就完全不发布任何动作**：没有东西可用来转码，而把一个注定会拒绝的工具摆给
智能体，只是白白浪费它的一轮。
