# Modelos do AI2P: como é organizado o catálogo

Este é o diretório com os documentos dos modelos: um arquivo para cada registro do catálogo de
modelos de IA, e o nome do arquivo é o **nome do modelo** (`Claude-Sonnet-5.md`,
`Qwen3.8-27B-Local.md`). Abre-se pelo botão **«i»** no formulário do modelo:
**Configurações → Catálogos → Modelos de IA**.

Aqui está o que é comum a todos: em que diferem as três formas de conexão, como colocar uma
chave, por que um modelo às vezes fica inativo e como criar um registro próprio.

## As três formas de conexão

| | em nuvem | local | pelo CLI |
|---|---|---|---|
| Onde calcula | o servidor do provedor | **o seu computador** | o servidor do provedor |
| Pagamento | por tokens | nenhum | **por assinatura**, 0 no faturamento |
| O que é preciso | **chave de API** | **baixar os arquivos** (dezenas de GB) | `claude login` neste computador |
| `provider` no perfil | `anthropic`, `openai-compatible` | `openai-compatible` | `anthropic` + `transport: cli` |
| `baseUrl` | o endereço do provedor | `http://localhost:<porta>/v1` | não é usado |
| Ferramentas do agente | as ferramentas do AI2P | as ferramentas do AI2P | **as ferramentas próprias do CLI** |
| Os dados saem para fora | sim | **não** | sim |

* **Em nuvem** — a maioria dos registros do catálogo. Rápido, de boa qualidade e pago; exige a
  chave do provedor e acesso à internet. Exemplos: Claude-Sonnet-5, GPT-5.6-Sol,
  DeepSeek-V4-Pro.
* **Local** (o nome termina em `-Local`) — os pesos ficam no seu disco, quem calcula é a sua
  placa de vídeo, e nada sai para fora. Chave não é preciso, mas são precisos espaço, memória e
  paciência para o download. Exemplos: Qwen3.8-27B-Local, Muse-Glimmer-30B-Local. O servidor
  local (`llama-server`) o próprio AI2P levanta ao iniciar o trabalho da equipe e desliga ao
  parar — **apenas o processo dele**; um processo alheio na mesma porta não é tocado.
* **Pelo CLI** (o nome termina em `_cli`) — o mesmo modelo em nuvem, mas executado pelo Claude
  Code em modo headless e pago **por assinatura**, e não por tokens. **A chave de API não é
  necessária**, é necessário ter feito `claude login`. Uma diferença importante: o agente
  trabalha com as ferramentas **dele** direto na pasta do projeto, e as ferramentas do AI2P não
  lhe são publicadas. Exemplos: Claude-Sonnet-5_cli, Claude-Fable-5_cli.

## Como colocar uma chave

1. **Configurações → Catálogos → Modelos de IA** — encontre o registro na lista.
2. O botão **«Definir a chave de API»** no formulário do modelo (se a chave já existir, ele se
   chama «Atualizar a chave de API»; o valor antigo nunca é mostrado).
3. Cole o valor fornecido pelo provedor e salve.

**A chave é comum a todos os modelos de um mesmo provedor.** No perfil de cada registro há o
campo «Chave nos segredos (referência)» — por exemplo `anthropic.apiKey` ou
`openrouter.apiKey`. Todos os registros com a mesma referência usam a mesma chave: informou-a
para o Claude-Sonnet-5 e o Opus e o Haiku passam a funcionar também. Onde exatamente obter a
chave está escrito no documento do modelo específico, na seção **«Como obter a chave»**.

A chave **pertence à organização**: ela é cifrada com a chave da organização e replicada para
todos os servidores dela, de modo que não é preciso informá-la em cada computador. A chave da
própria organização fica somente no computador dela (`secrets.json`) e nunca é replicada.

## Onde a chave fica em disco

A chave também pode ser definida por **arquivo** — é a segunda forma, para instalações sem
interface e para transferir chaves antigas. Os arquivos ficam no subdiretório **`secrets/` ao
lado do `config.json`** (ou seja, no diretório em que o aplicativo foi instalado), um json por
referência:

```
secrets/anthropic.apikey.json
{ "ref": "anthropic.apiKey", "value": "sk-ant-..." }
```

O caminho completo desse arquivo para um modelo específico aparece no formulário dele, na linha
**«Arquivo da chave neste computador»** — no mesmo lugar do botão de definição da chave. O
subdiretório é criado no primeiro início do aplicativo, e dentro dele fica a explicação
`readme.txt`.

**Uma chave informada no formulário não cria arquivo aqui**, e isso não é um erro: ela vai
cifrada para o banco da organização, para chegar aos demais servidores. O arquivo aparece nas
chaves do armazenamento em arquivo — as trazidas do antigo `secrets.json` no início e as
escritas à mão. Se esse arquivo existir, informar um novo valor no formulário atualiza também
o arquivo.

A ordem em que a chave é procurada: **banco da organização → `secrets/` → `secrets.json` →
variável de ambiente** (`anthropic.apiKey` → `ANTHROPIC_API_KEY`). O subdiretório `secrets/` não
entra na replicação, nem na distribuição, nem no inventário da instalação — na atualização de
versão ele fica intocado.

## Por que um modelo pode estar inativo

A marca «ativo» decide se o modelo é oferecido na escolha de executor. Ligá-la nem sempre é
possível, e isso é uma regra, não um erro:

* **um modelo em nuvem sem chave de API não pode estar ativo** — o formulário diz isso mesmo:
  «Sem chave de API: o modelo é ativado logo depois que a chave for definida», e a tentativa de
  ligar a marca pela API é rejeitada;
* **um modelo local sem os arquivos baixados não pode estar ativo** — «Modelo não instalado: é
  ativado automaticamente depois da instalação».

O sentido é simples: caso contrário o executor constaria como pronto, o trabalho iria para ele e
falharia já no início — com um erro de rede obscuro em vez de um claro «não há chave». Assim que
a chave for informada ou a instalação terminar, a marca se liga sozinha.

Daí decorre também que **um modelo `_cli` fica ativo de imediato**: ele não precisa de chave e
não há arquivos a baixar. A única verificação é se o Claude Code está instalado para o usuário
sob o qual o AI2P funciona; e essa verificação o AI2P não faz de antemão.

## Como acrescentar um registro próprio

O catálogo da distribuição é ampliado a cada nova versão, mas nada impede criar um modelo
próprio — por exemplo, o mesmo Qwen local em uma quantização menor ou o modelo de um provedor
que não esteja no catálogo.

1. **Configurações → Catálogos → Modelos de IA → «Adicionar modelo»**.
2. **Nome** — no formato `<nome geral>-<nome do modelo>`: `Claude-Opus-5.0`, `DeepSeek-V4-Pro`.
   Em um modelo local, acrescente o sufixo `-Local`. O nome tem de ser único.
3. **Alocação** — «Na nuvem (API do provedor)» ou «Local (funciona neste computador)».
4. **«Perfil…»** — provedor (`anthropic`, `openai-compatible`, `comfyui`), conexão (API ou
   agente CLI), **modelo (o id no provedor)**, Base URL, a referência à chave nos segredos, o
   comando de início do servidor local e os parâmetros (JSON, por exemplo
   `{"maxTokens": 32768}`).
5. **«Declaração de capacidades…»** — formatos de entrada e saída, habilidades com nota de 0 a
   100, limites (contexto, máximo da resposta) e o custo por 1 milhão de tokens. É por essa
   declaração que funciona a escolha automática de executor: **uma habilidade que não exista no
   catálogo de habilidades ninguém vai enxergar** — pegue os códigos da lista do formulário, não
   os invente.
6. Coloque a chave (se for em nuvem) ou aperte **«Instalar»** (se for local) — e ligue a marca
   «ativo».
7. **O documento do seu modelo** coloque aqui mesmo: `doc/pt/models/<nome do modelo>.md`. Se o
   documento não existir, o botão «i» mostra uma dica com o caminho completo de onde colocá-lo.

Os registros próprios são marcados como **«Personalizado»** e, ao contrário dos registros da
distribuição, podem ser excluídos por completo. Os registros da distribuição não podem ser
excluídos — se o modelo não for necessário, basta tirar dele a marca «ativo».

## O que não há nos documentos dos modelos

Os identificadores, os preços e os limites do catálogo foram conferidos com o catálogo público
de modelos e com um levantamento do mercado, mas **nenhum identificador foi verificado com uma
chamada real ao provedor**: o projeto não tem chaves para todas essas APIs. Por isso, em cada
documento de modelo em nuvem há sempre a mesma linha — antes do primeiro trabalho, confira o id
com uma requisição `GET /models` à API do provedor. O mercado muda depressa (cerca de um modelo
a cada dois dias) e um registro do catálogo fica desatualizado em silêncio: um id que mudou dá
404 já no executor, e um preço errado dá uma conta errada no faturamento.

Os requisitos de hardware dos modelos locais são uma **estimativa pelo tamanho dos pesos**;
medições em hardware real não foram feitas.
